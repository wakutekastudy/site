# ゲームページの作り方(game-page-guide.md)

わくてかスタディ研究所(wakutekastudy.com)の定番ゲームのページ(`classic-games/` の各ゲーム)を、新しく作る・改造するときのルールです。ゲームページは1本ずつ単独で作りますが、サイト全体の見た目と操作はそろえます。

- **コードの正本**:同じフォルダの `game-template.html`(ひな型)。共通部分はここからコピーします。
- **ルールの正本**:このファイル。ひな型のコードをこのファイルに書き写すことはしません(二重管理を避けるため)。
- `_dev/` フォルダはサイトの公開ページに含まれません(GitHub Pages の Jekyll は `_` で始まるフォルダを公開しない)。確認は手元のブラウザで行います。

**判断に迷ったら、「より単純・サーバー不要・より安全・流用しやすい」ほうを選びます。** 仕様にない機能は、実装する前に提案として出します。

---

## 1. ゲームページの位置づけ

| 項目 | 内容 |
| --- | --- |
| 中身 | 長く遊ばれてきた定番ゲーム(トランプ、盤ゲーム、パズルなど) |
| 目的 | 定番ゲームの「楽しさの仕組み」を研究し、学習ゲームに流用できるアルゴリズム(ルール判定、CPUの思考、シャッフルなど)を公開する |
| 作り手 | 運営者、または運営者の依頼で作るAI・開発者。第三者からのコード投稿は受け付けない |
| ライセンス | MIT-0(リポジトリの `LICENSE` を参照) |
| 形 | 1ゲーム＝1ファイル(`classic-games/<スラッグ>.html`)。ゲームどうしでファイルを共有しない |

将来は、第三者が書いた学習データを読み込む学習ゲームの土台になります。そのため、最初から学習ゲームと同じ技術・セキュリティの規約で作ります。

## 2. 題材の選び方(権利の確認)

次の3点で、他社の権利に触れないことを確認します。1つでも疑わしければ、候補から外すか、名称・見た目を変えて考え直します。確認結果はファイル先頭のコメントに書きます。

1. **ルール(メカニクス)**:遊び方そのものは原則として著作権の対象外。ただし、特定の企業が現在も強く権利を主張しているものは避ける。
2. **名称**:登録商標を使わない(例:「オセロ」ではなく「リバーシ」、「UNO」は使わない)。
3. **見た目の表現**:既存商品のカードの絵柄・特殊カードの名前・パッケージ・画面をまねず、独自に作る。

これは一般的な整理で、法的な判断ではありません。収益化などを予定するときは、専門家への確認を検討します。

## 3. 技術・セキュリティの制約

| 項目 | 制約 |
| --- | --- |
| ファイル | 1ゲーム＝単一のHTML(CSS・JSを内包)。300KB以内が目安 |
| 動作環境 | 主要ブラウザの最新2版。`file://` で開いても動くこと |
| 外部読み込み | しない(ライブラリ、CDN、Webフォント、画像ファイル、解析タグすべて)。例外はサイト共通のファビコン(`../assets/`) |
| 通信 | 一切しない(オフラインで全機能が動く) |
| 言語・ビルド | 素のHTML/CSS/JavaScript(ES2020程度)。ビルド工程・ESモジュールの `import` は使わない |
| 保存 | `localStorage` のみ(Cookie は使わない) |
| 絵 | CSS・SVG(`createElementNS` で組み立てる)・Unicode文字(♠♥♦♣など)で描く |

セキュリティ:

- `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `document.write` を使わない。文字は `textContent`、要素は `createElement` で作る。
- `eval` / `new Function` / 文字列を渡す `setTimeout` を使わない。
- 表示する文字列はすべてプレーンテキストとして扱う(将来、投稿データが入るため)。
- 保存データは `JSON.parse` のあと必ず検証する。通らなければ破棄して新しく始める。
- 盤の大きさ・手札の枚数・履歴の件数などに上限を設け、異常なデータで固まらないようにする。
- ひな型の `Content-Security-Policy` の設定をそのまま使う。

## 4. コードの分け方

1ファイルの中を、役割ごとのまとまりに分けます。ひな型の構成と名前に合わせます。

| まとまり | 役割 | 画面(DOM)への依存 |
| --- | --- | --- |
| `CONFIG` | ゲームごとの設定値(仮の値もここに集める) | なし |
| `TEXT` | 画面の文言(コード中に直書きしない) | なし |
| `rng` | シード付き疑似乱数、シャッフル | させない |
| `content` | 表示名など差し替えできるデータ(カード名、記号) | させない |
| `rules` | 初期状態、合法手、操作の適用、勝敗、保存データの検証 | させない |
| `ai` | CPUの手の選択。合法手の判定は `rules` を使い、ルールを作り直さない | させない |
| `storage` | 保存・読み込み・検証 | `localStorage` のみ |
| `ui` | 描画と操作。状態は直接書き換えず、必ず `rules` を通す | する |

状態・乱数・保存の約束:

- ゲームの状態は、JSONにそのまま変換できる1つのオブジェクト(数値・文字列・真偽値・`null`・配列・素のオブジェクトだけ)。`schemaVersion` を持たせる。
- 更新は `next = rules.apply(state, action)` の形。受け取った状態は書き換えず、新しい状態を返す。操作(`action`)も素のデータ(例:`{ type: "pass" }`)。
- ゲームのロジックでは、シードを指定できない標準の乱数を使わない。`rng` の疑似乱数を使い、シードを状態に保存する(同じシードと同じ操作なら同じ展開になる)。
- `localStorage` のキーは `wktks.game.<スラッグ>`(接頭辞 `wktks.` は全ゲーム共通)。
- コメントは日本語で、「なぜそうしたか」を中心に書く。

## 5. 共通パーツ(ひな型の使い方)

新しいゲームは `game-template.html` をコピーし、`classic-games/<スラッグ>.html` として作ります。ひな型の目印の意味は次のとおりです。

| 目印 | 扱い |
| --- | --- |
| `<style>` の「共通ここから」〜「共通ここまで」 | **全ゲームで一字一句同じ**にする。変えてよいのは `--gh-width` の値(ゲーム本体の幅)だけ |
| HTML の「共通ここから」〜「共通ここまで」 | 並び・見た目・文言をそろえる(id名は変えてよい) |
| 「標準の部品」 | 新しいゲームはこの形を使う。ゲームに合わせて調整してよい |
| 「★ゲームごと」「サンプル」 | ゲームごとに書き換える・置き換える |

画面の決まり:

- **上から順に**:戻りリンク「← 定番ゲーム一覧 ／ ホーム」→ 見出しの行(タイトル左、ボタン右)→ ルール欄(見出しのすぐ下に開く。最初は閉じる)→ メッセージ → ゲーム本体 → 対局後の「新しいゲーム (N)」。サイト共通のヘッダーメニューは入れない。
- **ボタン**:「ルール (R)」→「新しいゲーム (N)」の順。「新しいゲーム」は主ボタン(濃いオレンジ)。対局後にもゲーム本体の下に「新しいゲーム (N)」を出す(スマホで上に戻らずに始められるように)。
- **キー操作**:N=新しいゲーム、R=ルールの表示/非表示、Esc=ルールを閉じる。入力欄に文字を入れている間は反応させない。ゲームの操作(矢印キーなど)はこれと重ならないキーにする。
- **ルール欄の中身**:「ルール」「キーボード操作」「シード」(現在のシード、説明、指定欄、「このシードで新しいゲーム」ボタン)。
- **画面に出さないもの**:版番号、ライセンス、保存先、「ひな型」という言葉(これらはファイル先頭のコメントに書く)。
- **`<head>`**:ページタイトルは「〇〇 | 定番ゲーム | わくてかスタディ研究所」。説明文(`description`)は「〇〇をブラウザで遊べます。」＋一覧ページのカードと同じ説明。ファビコン・`theme-color` はひな型のまま。

**共通部分の確認**:ゲームを追加・改造したら、全ゲームの `<style>` の「共通ここから」〜「共通ここまで」を取り出し、`--gh-width` の行を除いて、ひな型と一致するかを比べます。共通部分そのものを変えたいときは、先にひな型を直し、全ゲームへ同じ変更を写します。

## 6. 配色とアクセシビリティ

配色はひな型の「標準の部品」の値を使います(ライトはクリーム地にこげ茶、ダークはこげ茶地にクリーム)。

| 用途 | ライト | ダーク |
| --- | --- | --- |
| 背景 / パネル | #FFF8EE / #FFEBD2 | #24170F / #33231A |
| 文字 / 薄い文字 | #3B2416 / #6E5443 | #FFF1E0 / #D9C3AE |
| カード・入力欄 / 枠線 | #FFFFFF / #E3CBB0 | #3A281C / #6E5443 |
| 主ボタン(背景/文字) | #B85215 / #FFFFFF | #F29A55 / #24170F |
| 手番・選択中の枠や印 | #E8792B(文字色には使わない) | #E8792B |
| 赤スートなど赤系の文字 | #B8321F | #FF9C8C |

- 文字の色は、背景とのコントラスト比4.5:1以上にする。
- 水色を使うときは、白と隣り合う箇所だけにする。
- 盤の色、直前の一手の印など、ゲーム固有の色はそのゲームのファイルで決める。
- `prefers-color-scheme` でライト/ダークの両方に対応する。文字の大きさは `rem` で指定する。
- モバイル(縦・幅375px)を優先し、横スクロールなしで遊べるようにする。ボタンなど押す場所は高さ44px(2.75rem)以上。
- スートや状態を色だけで区別しない(記号・文字も添える。例:♥7)。
- 手番の交代、CPUの行動、勝敗は `aria-live` で知らせる。フォーカスリングを消さない。
- CPUの手番は、何をしたか目で追える程度の間を置く(長くしすぎない)。

## 7. ゲーム画面の言葉

サイト全体の文章は、明るく肯定的で、やわらかい言い方にそろえます。急かす言葉・大げさな言葉(「今すぐ」「絶対」「最強」)は使いません。

| 項目 | 書き方 |
| --- | --- |
| 相手の呼び方 | 「CPU」。複数なら「CPU1〜CPU3」(空白なし) |
| 順番 | 「手番」(「あなたの手番です」「（手番）」)。手の数は「手数」 |
| 人数 | 「4人（あなた＋CPU3人）」 |
| 開始・再開 | 「新しいゲームを始めました（シード 〇〇）。」「中断したゲームを再開しました。」 |
| 保存データが読めないとき | 「保存データを読み込めなかったため、新しいゲームを始めました。」 |
| シードの入力エラー | 「シードには0以上の整数を入れてください。」 |
| シードの説明 | 「同じシードで同じ操作をすると、同じ展開になります。」。入力欄は「シード（整数）」 |
| 専門用語 | 短い補足を添える(例:「角のとなりのマス（X・C打ち）」)。直後に説明があれば不要 |
| かっこ・記号 | 日本語の文中は全角「（）」「＋」。キー名の「(N)」「(R)」、記号「●」「○」「♥7」はそのまま |
| 勝ち負け | 「負けです」「失格」はルールの説明なのでそのまま使ってよい |

## 8. ファイル先頭のコメント

GitHubで読む人がファイル単体で理解できるように、非公開の資料への参照(番号など)は書きません。ひな型の先頭コメントの見本に沿って、次を書きます。

- ゲーム名(日本語名/スラッグ)、版、最終更新日、ライセンス(MIT-0)
- 題材の確認(第2章の3点の結果)
- 採用ルール(ハウスルールの選択。例:パスは3回まで、ジョーカーなし)
- 流用できる部品(例:シャッフル、合法手の判定、CPUの思考)
- 転用メモ:①仕組みの核 ②学習への転用アイディア1〜3個(実装しない) ③差し替える箇所(例:`content.suits` と隣接判定の関数)

学習データの差し込み口:表示名や意味づけは `content` に置き、`rules` は「スート0の7番」のような抽象的な値だけを扱います。`content` は将来JSONとして外から読める素のデータにしておきます(読み込む機能は作らない)。

## 9. 作る手順

1. 第2章の3点を確認する。懸念が解消できなければ作らない。
2. 実装の前に、短いルール仕様(採用ルール、勝敗条件、CPUの強さの方針)を書き、運営者が確認する。
3. `game-template.html` をコピーし、`rules` → `ai` → `ui` の順に作る(`rules` 単体で動くことを確かめてから画面を作る)。
4. 第10章の受け入れテストを通す。
5. 一覧ページ(`classic-games/index.html`)への掲載は、運営者が決める。

## 10. 受け入れテスト

1. HTMLファイルをダブルクリックで開くだけで、最後まで遊べる(`file://`)。
2. ネットワークを切っても全機能が動き、外部への通信が1件も出ない。
3. ソースに `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `document.write` / `eval` / `new Function` が含まれない(文字列検索。コメントにも書かない)。
4. `rules` / `ai` / `rng` / `content` に `document` / `window` への参照がない。
5. 同じシードで同じ操作をすると、同じ展開になる。
6. 途中でリロードしても、続きから再開できる。
7. 保存データを手で壊しても(構文エラー・型違い)、止まらずに新しいゲームを始められる。
8. 幅375pxで横スクロールなしに遊べる。幅320pxでも崩れない。ライト/ダークの両方で読める。
9. キーボードだけで最後まで遊べる。N/R/Esc が第5章どおりに動く。
10. `<style>` の共通部分がひな型と一致する(第5章の確認)。
11. ファイル先頭に第8章のコメントがある。

## 11. AIへの禁止事項(善意でやりがちなこと)

- 「便利だから」とライブラリやCDNを読み込む
- 「描画が楽だから」とHTML/SVGを文字列から組み立てる
- オンライン対戦・ランキング・ログインを前提にする
- ゲームの状態をクラスのインスタンスやDOMの中に持つ
- ゲームのロジックで標準の乱数を使う
- ルール判定を `ui` に書く/`ai` がルールを独自に作り直す
- 転用アイディアを「ついでに」実装する
- 共通部分をそのゲームだけ変える(変えたいときはひな型から直す)
- 権利に懸念がある題材を、「ルールだけだから大丈夫」と名称や見た目を変えずに進める
